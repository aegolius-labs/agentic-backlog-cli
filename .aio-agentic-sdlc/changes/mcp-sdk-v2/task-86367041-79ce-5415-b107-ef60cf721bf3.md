# Migrate the MCP Integration to Python SDK v2

## 1. Architecture Overview

Migrate the existing stdio MCP surface from the Python SDK v1 FastMCP API to the reviewed stable SDK v2 MCPServer API without renaming or removing public operations.

Keep synchronous handlers synchronous and move thread safety into deterministic state and file
boundaries because SDK v2 runs them concurrently in AnyIO worker threads.

The compatibility baseline is 21 tools, two fixed resources (`backlog://current`,
`backlog://hierarchy-rules`), one prompt (`pick-next-task`), and the existing UVX stdio launcher.
Cross-repository resource addressing and new v2 product capabilities remain out of scope.

## 2. System Components

1. Dependency and server adapter: declare `mcp>=2.0.0,<3`, lock reviewed v2.0.0, import `MCPServer` from `mcp.server`, and preserve the stdio entry point and existing decorators. Do not pin `mcp-types` or `httpx2` independently.
2. Atomic backlog mutation: add one state-level mutation API that holds workspace-migration and state locks across recovery, load, mutation, revision increment, atomic replace, and prepared/committed audit records; refactor `core.py` mutators to use it without recursive public load/save calls.
3. Existing guarded state: retain the Intent DAG file lock and optimistic revision rules; retain mapping workspace and mapping locks and prove competing approvals are safe.
4. Semantic deduplication: protect project-local cache/schema writes with a file lock and serialize lazy model initialization/use; inject a deterministic test backend without changing production ranking behavior.
5. Artifact handlers: document generation uses guarded contained paths, per-output locking, temporary files, fsync, and atomic replace; spec promotion validates contained changes/spec paths, rejects traversal and reparse points, serializes the transition, and uses an atomic move; Reality generation validates that output stays inside the project before spawning and relies on the CLI DAG lock.
6. Protocol contract tests: exercise the complete surface through official v2 `Client` auto and legacy modes plus a real stdio subprocess.
7. Documentation and evidence: update the Codex plugin documentation and regenerate canonical Reality/reconciliation evidence only after the full QA gate.

## 3. Data Model

The public MCP contract is a normalized, deterministic inventory: operation kind, name or URI, description, parameter names, requiredness, accepted types, defaults, and result shape. No operation may be removed or renamed; no valid input may gain a required field, narrowed type, or changed default. Invalid-call error-channel corrections are permitted under MCP-V2-AC5.

Stateful mutation transactions preserve the existing backlog schema, revision, atomic replacement, and prepared/committed audit semantics. Test evidence records the installed MCP version, auto and legacy inventories, concurrency postconditions, protected-state hashes, cwd before and after, and exact canonical report hashes.

## 4. API Design

Implementation sequence is test-first:

1. Capture the normalized v1 public surface and make dependency-contract tests require `>=2.0.0,<3`.
2. Update the dependency and lock, then perform the minimal MCPServer port.
3. Add `Client(mcp, raise_exceptions=True)` auto-mode inventory and valid-call tests, plus equivalent `Client(mcp, mode="legacy")` tests.
4. Exercise all published tools, resources, and the prompt using isolated temporary projects and a deterministic semantic-model seam.
5. Reproduce concurrent backlog, audit, mapping, cache, document, promotion, and Reality-output races, then add atomicity until no lost updates or partial outputs remain.
6. Add invalid schema, unsafe path and URI, unknown operation, handler failure, and no-mutation tests.
7. Run a real local `aio-agentic-sdlc-mcp` stdio smoke test with the subprocess cwd set to the target project and validate the unchanged plugin launcher.

Evidence mapping:

- MCP-V2-AC1: dependency requirement, lock, and frozen sync.
- MCP-V2-AC2: exact surface and stdio tests.
- MCP-V2-AC3: full-surface auto and legacy clients.
- MCP-V2-AC4: repeated concurrent state tests.
- MCP-V2-AC5: deterministic errors and byte-identical failure-state tests.
- MCP-V2-AC6: warning-strict tests, static checks, build, validators, traceability, and reproducible canonical evidence.

## 5. Security Considerations

Expected domain and path failures return stable, bounded, non-secret MCP tool errors; unexpected failures use sanitized SDK internal-error behavior. SDK schema validation owns missing and wrong input rejection. Every failure test proves protected state is unchanged. Handlers never change process cwd.

Project paths and output leaves are guarded under locks against traversal, symlinks, Windows reparse points, and leaf swaps. Document and Reality outputs cannot escape the project. Concurrent writes preserve audit balance and revisions; genuinely stale external writers remain rejected.

Fixed resources retain their current cwd-based meaning and are tested through a subprocess started in the target project. The post-QA Cartographer must present a representative implementation symbol for explicit identity mapping; no GUID marker is inserted manually and mapping approval is not behavioral verification.
